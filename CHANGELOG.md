# Changelog

Notable changes to the AgenID reference implementation. Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

**Nothing in this repository has been released to npm or tagged.** Protocol version **v1.1.1** (plus errata E1 and E2) is the specification this implementation tracks; package versions are independent of it. Entries below are grouped by date and reference the commit that carried the change.

---

## [Unreleased]

### Removed
- **Three superseded DNS routes, and the credential-holding write path among them.** `POST /api/dns/verify` was a byte-for-byte copy of `POST /api/verify-dns`; `POST /api/dns/detect` duplicated provider detection that `POST /api/domain/status` does better; `POST /api/dns/auto-add` held a Cloudflare or GoDaddy API credential and wrote to the operator's zone. The last of those is **deleted rather than left unconfigured**, which is the substantive decision here: a credential-holding write path sitting unconfigured in the tree invites a future session to "finish" it, and the architecture decision went the other way in `1806e54` when `/verify/domain` shipped Domain Connect. AgenID does not hold write access to customers' DNS zones — that is the credential this product's entire argument is against. Test-enforced: no source file in `packages/web` may read `CLOUDFLARE_API_TOKEN`/`GODADDY_API_KEY` or call a provider's write API, and the whole `/api/dns` namespace must stay empty rather than half-populated.

### Changed
- **One DNS probe implementation, because the copies had already drifted three ways.** The `_agenid` TXT check existed in three places and provider detection in two, and the divergence was not hypothetical: (1) two routes built the record value from their own local `PREFIX` constant instead of calling `verificationRecord()`, so a change to the record's shape would have left them checking DNS for a value AgenID no longer asks for — matching nothing, forever, with no error anywhere; (2) `/api/verify-dns` carried the "domain control is evidence, not a level" disclosure and its byte-for-byte twin `/api/dns/verify` did not, so the honesty rule was enforced on one copy of the same endpoint; (3) `/api/dns/detect` did spec-literal Domain Connect discovery with no GoDaddy fallback, so the two endpoints disagreed about whether the same domain supported one-click. New `packages/web/lib/dns-probe.ts` is the only implementation, the disclosure is a shared constant rather than per-route prose, and the one behavioural difference that remains is deliberate and documented: a resolver failure is `502` on `/api/verify-dns`, which answered a direct question, and `pending` on `/api/domain/status`, which will ask again in six seconds.
- **The guard found two more copies than the search did, in the layer nobody thought to search.** After the routes were consolidated, the new test failed on `components/DomainFlow.tsx` and `app/onboarding/retell/page.tsx` — the UI built the record value by hand too. `DomainFlow`'s was the worse one: `record?.value ?? \`agenid-site-verification=${token}\`` is a *fallback* that silently disagrees with the source of truth, so before the first response landed the operator would be shown and would copy a stale record, publish it, and the flow would wait forever for something it told them to create. Every cell in that table (type, name, value, TTL) was its own literal; all four now come from the same builder the server uses. This is §10 of the integrity standard firing on the session that was applying it: *a fix scoped to the instance you found is a sample, not a fix.*
- **`/onboarding/retell` rewired onto the surviving routes**, and a stale capability claim removed with it — its Domain Connect pill read "AgenID has no Domain Connect implementation", untrue since `1806e54`. Its one-click button now renders only when `apply_url` is non-null, so it is absent until the service template is registered rather than being a link that 404s on someone else's dashboard.
- **The OpenAPI document now covers every deployed route — 13, up from 4 — and the correspondence is enforced in both directions.** The older half of the rule (never document a route that does not exist) was always enforced by review. The newer half exists because **omission is a claim too**: a machine-readable contract describing 4 of 13 routes told a security reviewer that two unauthenticated write paths, a credential-forwarding proxy and two outbound DNS amplifiers did not exist. `packages/web/test/dns-surface.test.ts` now fails on a route handler with no documented path *and* on a documented path with no handler. `scripts/check-docs.mjs` additionally asserts the three deleted routes return **404 in production** — a claim that would pass whether they were deleted or merely undocumented is a claim nobody is checking.

### Added
- **Rate limiting on every `POST` endpoint, and a batch-size cap — closes T-12, the last threat in the model that was exploitable today by anyone with an HTTP client.** Measured before the change: 25 rapid unauthenticated POSTs to `https://www.agenid.com/api/v1/agents` were all processed, with no `429` and no backoff. Two layers, and the ordering is the design: an in-process fixed window that **cannot fail** is applied first, then a durable counter in Postgres (`rate_limit_hit`, migration `0003`) that performs the increment and the decision in one statement so concurrent requests serialize on the row instead of racing. The consequence is the only honest definition of fail-open here — if the database is unreachable the limiter **degrades to per-instance limiting, never to unbounded**, and a test asserts exactly that by making 100 attempts against a broken durable layer and observing `burst` get through. The client is identified from platform-set headers (`x-real-ip`, `x-vercel-forwarded-for`), *not* from `x-forwarded-for`, which is caller-supplied: keying on it would let a caller mint a fresh bucket per request, which is a limiter that looks like one and bounds nothing — the same rule the key-discovery surface earned when it moved its decision onto the raw request target. IPv6 is collapsed to its /64 so one allocation is one bucket rather than 2^64 of them. The limit is checked **before the request body is read**, and a caller refused by the in-process floor never reaches the database, so the limiter cannot itself become the amplifier. `POST /api/retell/bind` additionally caps its `agents` array at 25 (`400 batch_too_large`): the rate limit bounds how many requests a caller may make, and without the cap it would have been a bound on nothing, since one request could still trigger an unbounded number of store writes. `rate_limit_counters` ships with RLS enabled and **no policies at all**, deliberately unlike every other table in the schema — per-caller request counts are operational telemetry, not registry data, and publishing them would make the limiter's own state a reconnaissance surface.
- **A wiring test, which is what found six more unbounded routes.** The gap analysis named four surfaces and the first pass bounded those four; a guard that walks every `route.ts` under `app/api` and requires each `POST` handler to call the limiter immediately failed on `/api/dns/auto-add`, `/api/dns/detect`, `/api/dns/verify`, `/api/verify-dns`, `/api/retell/declare` and `/api/v1/verify`. All ten are now bounded. This is the standing rule firing on the session that wrote it down: *a fix scoped to the instance you found is a sample, not a fix.* The guard also asserts the limiter is called **before** `req.json()`, and carries an explicit exemption list with a stated reason per entry, so a new unbounded public endpoint fails CI on the day it is added rather than on the day someone notices. Proven to fail: removing the limiter from `/api/v1/agents` turns three tests red.
- **`docs/SECURITY-GAP-ANALYSIS.md`** — the system evaluated against agent identity, human/organization binding, authentication, authorization, delegation and verification, with every claim established by reading the implementation or calling the deployed system. Its headline finding: AgenID is a credible identity and provenance layer with **no authorization layer at all**, so of the five questions an external verifier needs answered, two are answerable today and three are not. Records three gaps in the object model rather than in the code — there is no key role representing a human or an organization, so "who does this agent represent" is answered by an unverified free-text string (`GAP-B1`); verification levels describe how carefully an identity was checked and never what an agent may do (`GAP-D1`); and nothing binds a live HTTP request to a registered agent (`GAP-C1`). Includes the design for closing them as additive v1.2 objects in the `permissions`/`authorizations` namespace the specification already reserved, and states plainly that the security demo cannot be built honestly until they exist, because a demo that refuses an unauthorized action needs a permission model to refuse against.
- **`GET /v1/keys/{key-ulid}` — the registry half of two-path key discovery (spec §9.2), previously the only undeployed half of the mechanism that makes the registry non-authoritative.** Read-only, unauthenticated, no side effects: it serves a key document already in the store, verifies nothing, and reports no verification level. The spec-required query form `GET /v1/keys?key_id=<percent-encoded logical id>` returns a byte-identical document, produced by the same response builder rather than a second implementation. The path segment is the *wire* form of the key identifier (a bare ULID) while the store is keyed on the *logical* form (`agenid:key:<ULID>`); that is a protocol distinction, not a defect, and the only translation between them is `parseKeyReference` from `@agenid/core`, which also rejects a URI fragment in both its raw and `%23` spellings with `400 invalid_key_id`. A key that was never published is `404 key_not_found`, deliberately distinct from `agent_not_found`. Documents are re-validated against the strict `KeyDocument` schema before being served, so no stored column, internal field or future addition can reach a public response; error bodies do not quote the caller's input back. Every surface that said this path was not deployed — the README, `PROJECT_STATE.md`, `docs/api.md`, `docs/threat-model.md`, the operator onboarding guide and its web twin, the homepage two-path diagram, and every resolution envelope's `verify_instructions` — was corrected in the same commit.
- **`scripts/check-docs.mjs`** — documentation consistency check, wired into CI. Resolves every relative link, asserts the README's package list against the workspace, forbids dead hosts and overclaim vocabulary, asserts `L5` stays out of the issuable enum, and with `--live` verifies sixteen documented endpoint claims — asserting the error *code* where the documentation names one, since a bare status code cannot distinguish documented behaviour from a route that does not exist plus the OpenAPI version and path coverage against production.
- Regression test asserting `SupabaseStore` constructs on a runtime with no global `WebSocket`.
- Repository front door: `README.md` rewritten as a technical landing page, plus `LICENSE`, `SECURITY.md`, `CONTRIBUTING.md`, `CHANGELOG.md`, `PROJECT_STATE.md`, and `docs/architecture.md`, `docs/trust-model.md`, `docs/threat-model.md`, `docs/api.md`.

### Fixed
- **The key-discovery security decision was built on a framework's decoded path parameter, and a twice-encoded key ULID therefore resolved in production.** Measured against `www.agenid.com`: `GET /v1/keys/<ULID encoded twice>` returned **200**, while the identical code returned **400** under a local `next start`. The previous guard — reject a reference that still carries a `%` after "the" transport decode — assumed exactly one decode had happened, which is a property of the deployment platform rather than of the protocol. Vercel applies RFC 3986 path normalization ahead of the router and Next then decodes the dynamic segment again, so the guard was inspecting a value two decodes from the wire. The rule is now stated on the **raw request target**, where it needs no decode of its own: *the path segment, as it appears in the raw target, must be the literal wire form*, and a bare key-ULID contains no percent sign. That the extra decode belongs to Next rather than to the edge was proved, not assumed — `GET /v1/keys/%252F` reached the dynamic-segment handler, which is impossible if the platform had decoded twice before routing, since the path would have become `/v1/keys//`. The `?key_id=` value is now decoded by this registry itself, exactly once, from the raw query. Nothing beyond one layer of encoding resolves on any platform; the one thing a Vercel deployment cannot observe — a *single* layer of unreserved-character encoding, stripped upstream — is RFC 3986 §2.3 equivalence and is documented as such rather than glossed. `pnpm run check:docs:live` asserts the multiply-encoded targets against production and asserts the **reason**, not merely the status, because two different rules can produce the same code for the same target.
- **Fastify reflected the caller's complete request target in framework errors.** `FST_ERR_BAD_URL` is raised while find-my-way is still parsing, before routing, and its default body is `Invalid URL: <target>` — so `GET /v1/keys/<script>CANARY…%ZZ` came back carrying that string, from a surface whose own error text was carefully written not to do that, and from a route that never ran. `@agenid/api` now installs a framework-error handler and a global error handler that emit fixed AgenID sentences only: no framework message, no stack, no reflected target, and — via `rawKeyTargetFailure` — the same *reason* the handler itself would have given, so the two registries no longer agree on the status and disagree on why.
- **`/v1/keys` meant two different things depending on the framework in front of it.** Fastify answered `POST /v1/keys` with the authority key-publication path while the Next registry answered `405` and advertised `Allow: GET, OPTIONS`, which was therefore false on one of them. §9.2 defines `/v1/keys` as key discovery and defines only `GET` on it; publication is a capability of this reference registry, not a protocol method, and a public discovery URL that gates on a bearer token is an authority surface wearing a public address. Authority key publication moved to **`POST /v1/authority/keys`** with its behaviour unchanged, and key discovery is read-only on both frameworks: every mutating method on either the item or the collection resource is `405` with `Allow`, the CORS header and `no-store`. CORS on `@agenid/api` also stopped reflecting arbitrary origins (`origin: true`) in favour of one explicit credential-free `*`, matching what the Next registry already sent, and preflight is now answered per route so it advertises the methods the resource actually supports.
- **The cross-registry parity test compared two different requests and called them equal.** Its Next adapter passed `new URL(url).pathname`'s raw segment straight in as the route parameter — `URL.pathname` does not percent-decode — while `fastify.inject()` gave Fastify a target whose parameter find-my-way then decoded. For `/v1/keys/agenid%253Akey%253A<ULID>` the two registries were asked different questions, both answered `400`, and the assertion passed; neither representation was the one the real Next runtime produces. It is now driven from raw request-target fixtures, both adapters record the target they actually observed, `expect(nextRaw).toBe(fastifyRaw)` runs on every case, and each case asserts the **reason** and not only the code. Two false assertions in `keys-route.test.ts` were corrected rather than preserved, including one claiming "a percent sign can never survive into a lookup" that proved it by requesting the already-decoded identifier. End-to-end check `3l` likewise asserted only `400 invalid_key_id` — which the wire-form rule alone satisfies — so it passed while the protection it was named after was absent; it now asserts the specific reason, and checks `3o`–`3s` were added for the exact production defect, the platform boundary, non-reflection, and the collection method matrix.

- **Key references were decoded twice, so one key resolved under a family of spellings §0.A never defined — including double-percent-encoded ones.** A route handler is given an already-decoded value (Next.js decodes a path segment, `URLSearchParams` a query value, find-my-way a Fastify param), and `parseKeyReference` then decoded it again, because its contract is to accept a *raw* reference from a library caller. `GET /v1/keys/agenid%253Akey%253A<ULID>` therefore resolved `200`. A reference still carrying a `%` after the transport decode was encoded twice by its sender and is now refused before core is called, which also makes core's own decode provably a no-op — so the translation still goes through `parseKeyReference` and nothing was changed in `@agenid/core`, whose contract remains correct for the callers it was written for. Legitimate single percent-encoding is untouched: the transport removes it before anything here sees it. §0.A also gives each representation a *position* — wire form on the path, logical form in `?key_id=` — and each position now accepts only its own form, so one key has one spelling per position instead of eight.
- **Key discovery was implemented twice, with different security semantics.** `packages/web` re-validated the stored document against the strict `KeyDocument` schema, refused a document whose `key_id` disagreed with the identifier it was indexed under, and kept caller input out of its error bodies; the Fastify registry in `@agenid/api` did none of the three and interpolated the caller's own reference into its `400`. Production served the web one, so nothing was exposed — but `@agenid/api` is a deployable registry, and a protocol surface that answers differently depending on the framework in front of it is not one surface. Both now call `resolveKeyDocument` in `@agenid/api`'s new `serve-key.ts`; the routes are transport adapters. `packages/web/test/keys-parity.test.ts` drives the real handlers of both frameworks against the same fixtures and the same store and requires identical status and body — including for a polluted stored row, a mismatched index, a double-encoded reference and a duplicated parameter — rather than comparing source, which is what let the divergence survive review.
- **A repeated `key_id` query parameter silently resolved the first one.** Intermediaries disagree about whether the first, the last or a joined value wins, and §9.2 requires this form to return *the identical document*, which an ambiguous request cannot promise. `?key_id=A&key_id=B` is now `400 invalid_key_id` in both registries, in either order, and identical duplicates are refused too — nothing in the specification makes a repeated parameter meaningful.
- **Two hand-rolled `key_id.slice("agenid:key:".length)` translations survived in `packages/api`**, in the registration response's `links.key` and the authority key-publish response, while the test that forbids exactly that pattern read one half of one file in `packages/web`. Both now use `keyResolverPath` from `@agenid/core`, and the guard scans every file in both registries that participates in a key lookup. The only remaining prefix surgery in the repository is inside `keyIdToWire` itself, which is the sanctioned helper.
- **`405` responses on the key routes carried no `Allow` header, no CORS header, and a `public` cache directive that contradicted the route's own `no-store` policy.** RFC 9110 requires `Allow` on a `405`, and without the CORS header a browser-based verifier saw an opaque network failure instead of "wrong method". Both Next.js routes now export explicit handlers for `POST`/`PUT`/`PATCH`/`DELETE` built by the same response builder as every other key response, and the Fastify item route answers `405` rather than its framework default. No method reaches business logic in either.
- **Trust presentation failed open.** Both badges and the Verification Card mapped levels as `if (level === "L1_REGISTERED") -> amber; else -> emerald VERIFIED`, so an unrecognized, absent, empty or malformed level rendered as the strongest claim the product can make — produced by the absence of information rather than by any evidence. Nothing forged a signature; the presentation layer upgraded on ignorance. Now one canonical module (`packages/web/lib/trust-presentation.ts`) enumerates the four issuable levels and resolves everything else to a neutral, non-verified state. `public/badge.js` became a route generated from that module, so no consumer carries its own table.
- **`SECURITY.md` named a reporting channel that does not exist on this repository.** GitHub offers private vulnerability reporting only on public repositories, and `AgenID-protocol/agenid` is private — `PUT .../private-vulnerability-reporting` returns 404 for it. Enabled and API-verified on `AgenID-protocol/spec` and `AgenID-protocol/conformance` instead, and `SECURITY.md` now points there and explains why. It also records that `agenid.com` publishes no MX records, so no `security@` address on that domain can receive mail — a reporting address that does not receive is worse than none.
- **`/api/retell/bind` answered CORS preflight but sent no CORS header on its responses**, so a cross-origin browser POST cleared preflight and was then rejected at the response stage. Its sibling public write path sent the header on responses, so the two disagreed about whether they were browser-callable. Found by verifying a documentation claim against live responses rather than against a grep of the source. A test now requires the preflight and the response to agree.
- **Six fabricated claims in the API reference**, found by verifying it against the live deployment rather than re-reading it. The registration response shape was wrong (the level is nested under `verification`, and `status`, `manifest_digest` and `links` were missing); a `422` status was documented that the API never returns; `POST /api/v1/verify` was described as `ManifestProof` verification when it is a raw Ed25519 signature check taking `{manifest, signature, public_key_hex}`; the error-code table conflated three separate namespaces; the `503`/`registry_unavailable` path was undocumented; and `/a/<agenid>`'s deliberate representation split — `200` HTML card, `404` JSON — was documented as a flat `404`.
- **CI was red on the Node 20 leg of the matrix, and had been for several commits.** `createClient` builds a RealtimeClient eagerly, which probes for a global `WebSocket` — absent before Node 22 — so merely *constructing* a `SupabaseStore` threw on a runtime the package's `engines` field claims to support. The other two matrix legs stayed green and hid it. Both call sites now supply a transport that short-circuits the probe and throws loudly if a realtime channel is ever opened, since AgenID never uses one.

## 2026-09-14

### Added
- **Browser issuance flow (`/issue`)** — name an agent, generate an Ed25519 key in the browser, sign the manifest locally, and POST only public material. The private key never leaves the tab and is never written to `localStorage` or `sessionStorage` (test-enforced). `de83f5b`
- **`POST /api/v1/agents`** — the registration write path, deployed in `packages/web`, mirroring `@agenid/api`'s validation exactly. `de83f5b`
- **`GET /badge/<agenid>/shield.svg`** — static SVG badge for Markdown surfaces that strip scripts. Always returns 200, because a non-200 renders as a broken image rather than a badge. Unknown or malformed identifiers render neutral grey and read `NOT REGISTERED` — never red. `de83f5b`
- **`@agenid/cli`** — real key generation, manifest construction from explicit operator attestations, and `ManifestProof` signing over RFC 8785 canonical bytes. Private key written `0600` and never printed. `80672ca`
- **Client-side key custody** (`packages/web/lib/client-crypto.ts`) — browser Ed25519 via `@noble/curves` with its own JCS implementation, plus cross-implementation tests proving `@agenid/core` accepts a browser-produced proof. Two independent canonicalizers must agree byte-for-byte or the protocol quietly forks. `798c75d`
- **Bounded registration clock skew policy** (`packages/api/src/registration-time.ts`) — a proof created up to 120s ahead of the registry is evaluated at its own `created_at`; beyond that, `clock_skew_too_large`. `registered_at` is always the registry's clock. `verifyManifestProof` is untouched and remains strict. `be41a0a`
- Dedicated Supabase project provisioned, migration applied, production environment configured; cross-invocation persistence proven with real data. `3c97435`

### Fixed
- **Registry clock truncation would have failed essentially every registration.** Both write and read paths stripped fractional seconds, which only ever moves an instant *backward* — so a browser signing and POSTing within the same second produced `created_at > now` and the registry rejected its own fresh proof as `not_yet_valid`. The same truncation on the read path would have rendered a brand-new agent's badge as `PROOF INVALID`. `de83f5b`
- **`0001_registry_store.sql` could never have applied to any Postgres.** A `timestamptz` generated column cast from jsonb is not immutable (`42P17`). Rewritten as a plain column written explicitly — deliberately not as `text`, because lexicographic order disagrees with chronological order across mixed fractional-second precision. `3c97435`
- **Storage backend changed a protocol field's serialization.** Postgres renders `timestamptz` with a numeric offset while `MemoryStore` round-trips `Z`, so the same agent's `registered_at` differed between the POST response and the resolution envelope. Normalized at the store boundary. `be41a0a`, `f9c68d7`

### Security
- **Fabricated-verification stubs removed.** A generated CLI and three generated API routes asserted verification outcomes without computing any — including a route that returned `ORGANIZATION_VERIFIED` for any domain submitted to it, and a hardcoded DNS token identical for every user and every domain. Replaced with real Ed25519 paths that report `DECLARED` and nothing above it. `80672ca`
- **Server-side operator key generation deleted outright** rather than hardened. `key-encryption.ts` silently wrote `plain:<hex>` whenever its secret was unset. The registry now never holds an operator private key, by construction. `798c75d`
- **Forged operator identity and disclosure attestations removed from `/onboarding/retell`.** Every operator using that public page had been signing a fixed operator name, contact, purpose, and `discloses_to_user: true` / `human_escalation: true` — under their own key. `1a52a2c`, `ea3ff9b`
- `DECLARED` had been rendering in Verified Emerald with confetti despite sitting *below* L1. Now amber, and the panel states plainly that no third party has checked the claims. `1a52a2c`
- Dead and out-of-namespace hosts removed from public copy (`app.agenid.ai`, `api.agenid.com`), and undeployed endpoints — the second key-discovery path and the assertion write path — explicitly labelled as not deployed in the docs, the homepage diagram, and every Verification Card's `verify_instructions`. `1a52a2c`
- A "Privacy Escrow Guarantee" describing an escrow that does not exist was removed. `1a52a2c`
- Root `package.json` `"private": true` guard restored after being deleted — it is the only thing preventing a root `npm publish` from publishing the entire monorepo. `80672ca`
- New `packages/web/test/public-surface.test.ts` makes each of the above a build-breaking assertion rather than a review convention. `1a52a2c`
